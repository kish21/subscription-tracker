### Goal
Enforce the allowed-currency list at the signup boundary, so an account cannot be created with a
currency the product does not support.

### Slice Strategy
- [x] Ad-hoc - bug / edge-case / tech-debt / security

### Classification
`bug` (data integrity; not exploitable for denial of service - see below)

### Affected Files
- `src/auth/server.ts`
- `tests/integration/auth.test.ts`

### What happened
`currency` is declared as a Better Auth additional field with `type: 'string'` and `input: true`
(`src/auth/server.ts`). The Zod `currencySchema` that restricts it to the six allowed ISO-4217 codes
is applied only in the client form (`src/components/features/auth-form.tsx`). A direct POST to
`/api/auth/sign-up/email` therefore bypasses it.

### Expected vs Actual
- **Expected:** a currency outside `product.yaml -> currency.allowed` is rejected at the boundary.
- **Actual:** any 3-character string is accepted and stored.

### Reproduction (verified live on 2026-09-10)
```bash
curl -X POST localhost:3000/api/auth/sign-up/email -H 'content-type: application/json' \
  -d '{"name":"Z","email":"zzz@test.com","password":"Password12345!","currency":"ZZZ"}'
# => 200, user created with currency ZZZ
# GET /dashboard  => 200, totals render as "ZZZ 27.57"
```

### Severity - measured, not assumed
An earlier review suggested a longer invalid code (e.g. `BOGUS`) would reach
`Intl.NumberFormat` and throw `RangeError`, permanently 500-ing that account's dashboard. **That was
tested and does not happen:** a 5-character value is refused by the `varchar(3)` column
(`FAILED_TO_CREATE_USER`, 422), and a well-formed 3-character code such as `ZZZ` does not throw -
`Intl` falls back to printing the code verbatim. So the impact is **mislabelled totals**, not a
crash or a denial of service.

### Suspected cause
The validation lives in the UI layer only; the auth adapter's `additionalFields` type system is
weaker than the Zod schema the rest of the codebase uses at boundaries.

### Implementation Tasks
- [ ] Validate `currency` against `ALLOWED_CURRENCIES` server-side in the Better Auth config
      (`validator` / `before` hook), sourcing the list from config - never a hardcoded literal.
- [ ] Return a 400 with a typed error envelope, consistent with the other boundaries.
- [ ] Add an integration test posting `currency: "ZZZ"` directly and asserting rejection.
- [ ] Decide the fate of existing rows with an unsupported currency (none in production yet).

### Security in the Definition of Done
- [x] Validation at the boundary, not in the UI; the client remains a convenience only.
- [x] Fails closed: an unrecognised currency is rejected, never silently defaulted.
- [x] Regression test proves the direct-POST bypass is closed.
- [x] No secrets touched.
